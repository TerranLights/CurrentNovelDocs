## 1 · What this plan is for

From **2026-10-29** the developer moves from Max 5x to **Max 20x** and intends to "power bulldoze" through as much of the universe's material as possible over about **four to six months**. The plan exists to (a) keep that effort on track and focused, (b) use every working hour and every allotment efficiently, and (c) let any repo's session find out in one read what is being done, in what order, and why.

## 4c · Ongoing background task: C++ benchmark suite (added 2026-10-27)

**Developer's request (2026-10-27):** run benchmarks on C++ design patterns and data layouts to find which are the most CPU-efficient. **Priorities, in order: raw speed, system-resource efficiency, optimization.** The target is nanosecond-scale operations where that is achievable. The results will also shape the architecture of the developer's other games, not only Inner Tepenia.

| Item | Decision |
|---|---|
| **Order** | **Game-relevant set first** (Inner Tepenia's engine hot paths: grid and pathfinding, damage calculation, turn and AP queues, entity updates), **general C++ patterns after.** |
| **Where it lives** | A standalone benchmarks folder, most likely inside `games/Inner Tepenia/InnerTepeniaDEV` (shared across games, so the folder is kept independent of any one game). Final location to be confirmed when the folder is created. |
| **First and largest test family: data layout** | Arrays, because a CPU is fastest on contiguous data. The key question is how to keep objects fast: array of structs vs struct of arrays vs index/handle-based pools vs plain heap objects, for realistic game workloads. Other structures (linked lists, hash maps, trees, flat sorted vectors) are compared against arrays so the cases where an array is *not* the right answer are measured, not assumed. |
| **Later families** | Dispatch (virtual vs CRTP vs `std::variant` vs function pointers vs templates), allocation (pools, arenas, plain `new`), event and observer patterns, branch-heavy vs branch-free code, and the GDExtension boundary cost between GDScript and C++. |
| **Second major family: memory management and the seamless streaming world** (developer, 2026-10-27, "extremely important") | The goal is a world that works like Cyberpunk 2077's: cells of the world are loaded into and unloaded from RAM dynamically as the player moves, so the world feels seamless. **The only loading screens allowed are (1) loading a save file and (2) fast travel.** Tests: cell load/unload cost and hitching (frame-time spikes) while moving, background streaming on a worker thread, allocator strategies for cell data (per-cell arenas, pools, plain heap), fragmentation over long sessions, peak and steady-state RAM, and the cost of the boundary between GDScript/Godot and C++ for streamed data. |
| **Leak testing: never any memory leaks** | Tested "extremely extensively": AddressSanitizer and LeakSanitizer on every test, Valgrind and heaptrack passes, and long soak tests that load and unload cells millions of times and check that RAM returns to a flat baseline. **Design rule that goes with it:** ownership by construction (RAII, one owner per allocation, whole-cell arenas freed in one step), so leaks are prevented structurally and testing confirms it. Testing alone can show no leak under the conditions tried; it cannot prove none can exist, so the structure matters as much as the tests. |
| **Hardware-thread constraint** | **Every family is also run restricted to two hardware threads (two cores)**, so the results hold for a player on a quad-core CPU without an 8- or 16-core machine. On this Linux machine that is done by pinning the process to two cores (`taskset`), choosing two different physical cores rather than two hyperthreads of one. The pinned runs measure thread count only: a typical quad-core CPU also has lower clocks and smaller caches than the 5700G, so absolute times will still be better here than on that player's machine. |
| **Method** | A single harness (Google Benchmark, installed locally); each test run at several optimization levels; both warm-cache and cold-cache runs, since real game frames run cold; guards against the compiler deleting the measured code; every result recorded with CPU, compiler and flags. |
| **Test machine** | AMD Ryzen 7 5700G, 16 hardware threads, g++ 13.3 (Ubuntu 24.04), as of 2026-10-27. Results rank patterns *on this hardware*; they are re-run when the hardware or compiler changes. |
| **Reference target player machine** (developer, 2026-10-27) | **The design assumption is a player on a quad-core AMD Ryzen 5 with an NVIDIA GeForce RTX 2000-series GPU** (**confirmed 2026-10-27: the RTX 2060**; the developer first wrote "2040", which is not a real card). All speed, memory and streaming budgets are judged against *this* machine, not the 5700G. **How:** (1) the 5700G runs are pinned to 2 and 4 cores and, where possible, clock-capped, as an approximation; (2) the 5700G has only integrated Radeon graphics, so **no RTX-specific GPU result can be measured here**: GPU-side budgets (draw calls, VRAM, texture streaming) stay unmeasured until real hardware is available; (3) **recommended:** a used machine matching the reference spec (an older quad-core Ryzen 5 with an RTX 2060 is inexpensive second-hand) as a dedicated test box, so the final numbers are real instead of approximated. Decision for the developer; nothing is bought or assumed until they decide. |
| **Test laptop (developer, 2026-10-27)** | The developer will buy a dedicated testing/experimentation laptop for the C++ pressure-testing. **Baseline: Baldur's Gate 3's official minimum spec** (Windows 10 64-bit; Intel i5-4690 or AMD FX 8350; 8 GB RAM; GTX 970 or RX 480 with 4 GB+ VRAM; verified against the Steam requirements 2026-10-27), as the floor the games must still run on. The quad-core Ryzen 5 + RTX 2060 entry above stays as the mid-tier target. **Buying notes (for the developer):** (1) a new laptop will usually be *faster* than this floor, so the floor is approximated by pinning to 2 and 4 cores and capping clocks, or by buying an older used machine; (2) laptops throttle with heat, so every run is done plugged in, on the performance power profile, with the CPU temperature logged; (3) the GPU should be checked against a benchmark chart before buying (roughly the GTX 1050 Ti / 1650 class is the neighborhood of a GTX 970; not yet verified); (4) players are on Windows, so every family is also built and run on **Windows with the same compiler the Godot export uses**, not only on Linux, since compiler differences change results; (5) 8 GB RAM and 4 GB VRAM are the memory ceilings the streaming-world tests must fit inside. |
| **Cost** | Almost no usage allotment: Claude writes the tests once, then they run locally. It can run at any hour; the ULM operating-hours law does not apply to it. |
| **Output** | One results table per family plus a short written recommendation per family, in the benchmarks folder. |

**Status:** not started. **Next step:** confirm the folder location, install the harness, and write the first data-layout family.

## 5 · Dependencies that shape the order

- **Everything in the GDD derives from the 38 cities:** weapons, factions, religions, districts, music. None starts before the city corpus is done.
- **Founders come from the GDD's Founding Register**, which in turn depends on the post-war nations built in this worldbuilding folder. Europe's Italy split and the CIN are the current live case (`worldbuilding/nations/Europe - GDD hand-over intake…`).

- **Post-war conditions wait for the complete model of every city** (ULM, CST and RWBEM all finished). You cannot work out how a place collapsed until you know what it was like when it worked. Until then, the post-war spec fields (`Status`, `Connection to Concordia`, `Current Status`, `Legacy`) stay marked as not an input to any pass, exactly as the ULM already treats them.
- **Vignettes follow each wave**, and each wave follows the previous one strictly.
- **Megasheets are rewritten only after all three processes**; do not edit them meanwhile.
- **Operating hours:** ULM/CST/RWBEM only 05:00 to 14:59. Everything else is any-hour work and is where the gaps get filled.
